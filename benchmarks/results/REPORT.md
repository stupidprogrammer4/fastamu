# اندازه‌گیری واقعی repositoryها — 2026-09-13

هر شش دیتابیس اجرا شدند. مسیر فعلی bulk update در batch هزارردیفی روی SQLite، PostgreSQL، MySQL و MariaDB از CASE سریع‌تر بود؛ Oracle در همین اندازه timeout داد و SQL Server با تعداد پارامترهای این statement خطا داد. بنابراین تأیید بدون قید برای تمام backendها درست نیست.

در این نوبت کد production تغییر نکرد؛ اسکریپت‌ها و نتایج benchmark اضافه شدند.

## محیط و اعتبار مقایسه

۱۰۰٬۰۰۰ ردیف، دو ستون عددی برای update، دو warmup و ۹ نمونه برای هر حالت سریالی. زمان‌های جدول‌ها median و برحسب میلی‌ثانیه‌اند. ساخت و compile کوئری، execute و تبدیل نتیجه داخل زمان‌اند؛ checkout و rollback خارج زمان سریالی‌اند. نوشتن‌های سریالی rollback می‌شوند. آزمایش هم‌زمانی commit واقعی دارد. جزئیات در [روش اجرا](../README.md) و [محیط و hash کدها](environment.json) آمده است.

CPU: AMD Ryzen 7 3750H، هشت CPU منطقی، حدود ۱۵ GiB RAM؛ Python 3.13.7، SQLAlchemy 2.0.49، SQLModel 0.0.38. هر بار فقط یک دیتابیس benchmark روشن بود؛ سرویس‌های قبلی میزبان فعال ماندند. SQLite روی دیسک workspace بود. SQL Server محدودیت حافظهٔ 1536 MB داشت و Oracle نسخهٔ XE بود. این جدول‌ها برای مقایسهٔ روش‌ها در هر دیتابیس‌اند؛ رتبه‌بندی سرعت محصولات نیستند.

- عدد ۵۰۰ تضمین عمومی برای اندازهٔ batch نیست؛ تعداد ستون‌ها و پارامترهای دیگر هم مؤثرند. راه‌حل بعدی SQL Server باید بودجهٔ پارامتر را لحاظ کند. برای Oracle ابتدا علت timeout باید مشخص شود.
- در batchهای کوچک، grid همیشه سریع‌تر نیست. اختلاف کوچک در این نمونهٔ کوتاه اثبات برتری پایدار نیست.

## MySQL: درج گروهی با دو قرارداد خروجی

این نتایج مربوط به نسخهٔ پیش از حذف `MySQL.bulk_create` هستند؛ نام ستون‌های تاریخی حفظ شده است. کد benchmark اکنون همان مسیر قدیمی را با نام `orm_refresh` فقط برای مقایسه بازسازی می‌کند.

`bulk_insert` تعداد درج را می‌دهد؛ `bulk_create` مدل‌های کامل با مقادیر تولیدشده را برمی‌گرداند. هر دو همان ردیف‌ها را ذخیره کردند، اما هزینهٔ خروجی یکسانی ندارند. شمارش SQL شامل verification و کنترل transaction نیست.

## حدود نتیجه

این اندازه‌گیری مسیرهای update، درج MySQL و pagination را پوشش می‌دهد؛ benchmark کامل framework، upsert، projection، event delivery، دادهٔ JSON بزرگ، بار طولانی، خرابی شبکه یا تضمین عدم گم‌شدن پیام نیست. از این اعداد نمی‌توان «کل framework آمادهٔ production است» نتیجه گرفت. دو مسئلهٔ عملیِ اندازه‌گیری‌شده پیش از تأیید batchهای بزرگ باقی‌اند: Oracle timeout و سقف پارامتر SQL Server.

فایل‌های `pilot/` در جدول‌ها استفاده نشده‌اند. پنج بخش هم‌زمانی پس از اصلاح warmup pool دوباره اجرا شدند و جای نسخهٔ قبلی نشستند؛ SQL Server از ابتدا با warmup اصلاح‌شده اجرا شد. کد production در این فاصله ثابت بود. صفر بودن `runner_failures.json` فقط پایان موفق harness را می‌گوید؛ خطاهای عملیات داخل JSON هر دیتابیس محفوظ‌اند.
